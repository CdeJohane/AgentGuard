AGENT GUARD - LEARNING LOG

25 October 2026

Project: Learning to build a Python security guard for AI agent actions.

What I did:
- Initialized a Git repository for the project.
- Implemented a permission rule allowing only reading notes.txt.
- Implemented input validation for dictionary structure, required keys, and
  string values before checking permissions.
- Ran simulated requests covering allowed actions, forbidden actions, and
  malformed input. The simulation produced one ALLOW and ten DENY decisions
  without errors.
- Wrote three validation tests: a valid read request, a well-formed but forbidden
  write request, and a request missing its path. At that stage, all eight
  automated tests passed, with none skipped.
- Implemented check_request() to return a boolean decision and a string reason
  for allowed requests, malformed requests, forbidden actions, and forbidden files.
- Implemented execute_request() to call the guard before simulated execution.
  Allowed requests return the simulated contents; denied requests preserve the
  guard's reason and never call the reader. All eighteen tests passed.

What I learned or explored:
- An agent can propose an action, while a separate guard checks permission.
- Default deny: an action is refused unless explicitly allowed.
- Fail closed: invalid input should be denied without crashing the guard.
- Valid input and permitted actions are different: a write request can be
  well formed and still forbidden.
- Python's 'and' short-circuits, so validation can protect later key lookups.
- Type annotations document expected inputs but do not enforce them at runtime.
- Used unittest assertions to check expected results automatically, including
  testing validation separately from permission decisions.
- Explored tuple unpacking and why a nonempty tuple containing False is truthy.
- Used ordered checks to choose a consistent reason when several rules fail.
- Explored an enforcement point: the execution function checks permission before
  calling an operation, so a denial actually prevents execution through that entry.
- Used mock-based tests to verify the reader is called once for allowed requests
  and never for forbidden or malformed requests.

Pair-programming support:
- The simulation and documentation were scaffolded with assistance.
- Automated permission tests and a validation-test exercise were added using
  Python's built-in unittest module.
- The initial test run passed all five permission tests. I then completed the
  three validation tests myself and removed their skip lines.
- The request annotation and leftover scaffold comments were tidied with help.
- is_allowed() was connected to my check_request() implementation with help,
  so the permission rules now live in one place. Message wording was standardized
  and an unreachable placeholder return was removed.
- Six reason tests were added with help, covering all outcomes and check priority.
  All fourteen automated tests passed, with none skipped, and the simulation
  displayed one ALLOW and ten DENY decisions with reasons and no errors.
- A simulated reader and four execution tests were supplied with help; I wrote
  the execution function. All eighteen tests then passed, with none skipped.
- The project was reorganized with help: application modules in agent_guard/,
  tests in tests/, and this learning log in docs/. Imports and mock targets were
  updated for the package layout without changing permission or execution rules.
- After the move, all eighteen tests still passed and the simulation produced
  the same decisions and reasons using the new module command.

Packaging concepts to review:
- __init__.py marks the application and test directories as Python packages.
- A relative import such as 'from .guard import check_request' refers to a module
  in the same package. Tests use imports such as 'from agent_guard.guard import ...'.
- Run the simulation from the project root with 'python -m agent_guard.simulate'.
- Mocks now target 'agent_guard.executor.simulated_read', where the executor
  looks up its reader. The full test command remains 'python -m unittest -v'.

Next step:
